# AI 架构工作规范

本项目以架构编辑器中的 Node 树描述功能边界，以接口引用描述模块之间实际使用的能力。AI 在新增功能、修改行为或重构模块时，应先阅读本规范和 [`architecture.json`](architecture.json)，再结合代码确定实现位置。架构文本说明意图，代码呈现已实现行为；两者不一致时，应查明差异并在工作范围内同步，不能默默扩大模块职责。

## 1. Node 是功能边界

- 每个画布 Node 表示一个功能模块。`functionText` 写明该实例负责的行为、边界和必要约束；实现可以自行选择类、文件、算法和具体方法，但不能超出这些职责。一个 Node 不必对应一个类或文件。
- Node 的接口列表描述它向其他模块开放的能力。每项有稳定 `id`、`title` 和自由文本 `content`；接口文档不规定代码参数或方法签名。接口内容应说明能力的行为、可观察结果和关键约束；具体 C# 签名由实现决定，并应与说明一致。
- 模块内部的私有实现细节不必逐一建接口。其他 Node 若要依赖某项能力，应通过该模块已有或新增的接口表达，不能因为能直接访问代码就绕开边界。
- 空白的功能或接口文本表示尚未定义，不表示该模块可以承担任意职责。需求无法从现有文本确定归属时，先根据用户需求和代码补全或澄清边界，再实施有争议的行为。

## 2. 父子关系与接口引用是两种不同关系

- `parentId` 表示“子功能是父功能的延伸或细化”，两者有强相关性。优先把新 Node 放在最贴近其职责的父 Node 下；Root 表示项目级范围。父子关系不要求对应 C# 继承、嵌套类或目录结构。
- 父 Node 提供功能背景，但不自动授予子 Node 实现父 Node 全部职责的权限。父子之间也不自动存在接口调用。
- 如果一个 Node 实际使用另一个 Node 的接口，即使两者有父子关系，也要单独记录接口引用。反过来，两个 Node 有接口引用，不意味着它们应成为父子。
- 编辑器允许尚未连接父节点的 Node 独立存在并保存。未连接不影响它的功能和接口；确定了功能归属后再建立父子连线，不要为了“连上树”而选择语义不合适的父节点。

例如，`B` 是 `UI` 的子功能，同时 `B` 使用 `A` 的“读取状态”接口：`B.parentId` 指向 `UI`，接口引用则从 `A` 的该接口指向 `B`。两条关系都要保留，不能互相替代。

## 3. 优先复用接口，并记录真实依赖

新增功能需要其他模块提供能力时，先搜索已有 Node 和预制模块的接口，阅读标题与内容，并核对提供者的功能边界及代码实现。只在语义确实匹配时复用，不因名称相似就视为可用；若接口已有文档但尚无实现，先补齐提供者的能力，不能假定它已经可调用。

若没有合适接口，先判断能力是否仍属于现有提供者的功能范围：属于时，可为其新增接口；不属于时，应选择更合适的 Node 或创建新模块。不要为了复用而扩大旧模块的职责，也不要重复创建已有能力。

当模块 `B` 实际使用模块 `A` 的某个接口时，在 `interfaceReferences` 中记录一条从提供者到使用者的引用：

| 字段 | 含义 |
| --- | --- |
| `sourceNodeId` | 提供接口的具体画布 Node ID，即 `A.id` |
| `interfaceId` | `A` 实际接口列表中该接口的稳定 ID |
| `consumerNodeId` | 使用接口的具体画布 Node ID，即 `B.id` |

每条引用还应有自己的唯一 `id`。同一提供节点、接口和使用节点的组合只记录一次；模块不能引用自己的接口。引用表示真实的跨模块依赖，不是计划中的调用，也不是仅因两节点存在父子关系而自动生成的连线。删除或替换接口、移除依赖、删除 Node 时，同步检查和清理相关引用。

## 4. 预制模块与实例

- `templates` 中的 `presetText` 描述预制模块对**所有实例**共同适用的功能和约束；预制接口列表也由各实例共享。
- 画布 Node 的 `functionText` 描述**这个实例**的具体职责。使用预制模块时，AI 必须同时阅读预制文本和实例功能文本，并让实现同时满足二者。实例文本不是预制文本的副本，也不能默默覆盖预制约束。
- 若需求只影响一个实例，优先修改该实例的功能文本或为它增加合适的子 Node；若需求应影响所有实例，再修改预制定义，并检查每个实例的影响。
- 预制定义的固定子节点会同步到现有实例。不要把固定子节点当作可随意改挂的普通节点；所有模块仍可按需要附加非固定的子模块。
- 若预制文本、实例文本或父节点职责互相矛盾，先指出冲突并确定边界，再选择实现；不能只读取其中一处。

## 5. AI 执行一次功能变更的顺序

1. **定位范围**：读取架构数据，找到受影响 Node、其父链、相关预制定义、现有接口和引用；再查找对应代码。不能仅凭画布位置、显示名称或类名推断归属。
2. **决定归属**：确认需求能否落在已有 Node 的功能边界内。若超出边界，先形成明确的架构变更，例如新增子 Node、调整功能文本或补充接口；不要把新行为直接塞进旧模块。
3. **设计依赖**：优先检查可复用接口，确定具体提供者与使用者。需要新接口时写清标题和行为内容；不要在架构文本里臆造尚未确定的参数列表。
4. **实现代码**：让公开能力与接口说明一致，内部实现保持在相应 Node 的职责内。跨 Node 使用已有能力时，以接口语义为约束，避免直接依赖提供模块的内部细节。
5. **同步架构**：更新受影响的功能文本、接口和实际引用。保留未改变实体的稳定 ID；只为新 Node、新接口和新引用生成新 ID。预制变更要核对所有实例。
6. **核对结果**：确认代码行为未越界、接口引用与实际依赖一致、没有失效引用，`architecture.json` 仍能被编辑器读取并通过结构校验；运行与改动相关的代码验证。交付时说明架构与代码各改了什么，以及仍有的边界歧义。

## 6. 架构数据的解释规则

从 `Assets/Architecture/architecture.json` 读取 Node、预制定义和接口引用。普通 Node 的接口取自自身 `interfaceItems`；预制实例的有效接口取自其 `templateId` 指向的预制定义 `interfaceItems`。引用必须使用有效接口的 ID，而不是标题文字。

`position` 只控制画布位置；展开、折叠是视图状态，不构成功能声明。以 Node 的功能文本、有效接口和预制文本解释职责，不用兼容旧数据的字段推断新功能边界。结构校验不能证明自然语言功能描述与代码语义一致，这部分需要 AI 和开发者核对。

若同时在编辑器与外部修改 JSON，先保存编辑器中的架构变更，再编辑文件并让编辑器重新读取，避免覆盖未保存内容。不要为文档同步而批量重排 JSON 或改写无关字段。
