# 架构 Node 功能实现

处理本项目的功能模块、接口或模块间依赖时，先读仓库根目录的 [AI 架构工作规范](../../../Assets/Architecture/AI_WORKFLOW.md) 和 `Assets/Architecture/architecture.json`。规范解释字段语义；JSON 提供 Node 实例、预制定义与引用关系。仅讨论编辑器界面而未涉及功能模块时，无须套用本流程。

1. 找到受影响的 Node，读其 `functionText`、父链及有效接口；预制实例还要读对应 `presetText`、预制接口和固定子节点。结合现有代码确认实际职责。功能文本为空或互相冲突时，不把空白当成无限制授权。
2. 为新需求选择边界内的现有 Node，或定义职责明确的新 Node 与合理父节点。父子关系表示功能延伸，不能代替跨模块接口依赖。
3. 搜索已有接口并优先复用语义匹配的能力。若需新增能力，确认提供者仍在自身边界内；接口只写标题与行为内容，具体参数留给代码实现。
4. 功能行为发生变化时，必须同步到对应 Node 的 `functionText`；对外能力或跨模块依赖变化时，也要同步接口和 `interfaceReferences`。预制实例的有效接口来自预制定义。保留不变实体的 ID，并清理失效引用。
5. 在新增 Node 或改写 Node 文档（功能文本、接口、父子归属、引用记录或预制定义）前，先向用户展示具体方案：受影响的 Node 或预制定义、拟改字段及文本、修改理由、父子关系、接口引用和其他实例的影响。征得同意后再写入架构数据；如果用户已经明确同意该具体方案，不重复征求同意。未经同意，不把拟议的 Node 文档改动落盘。
6. 核对代码职责、预制定义与实例文本、接口说明和引用记录是否一致；验证架构文件可读取，并运行相关代码检查。总结本次功能边界及依赖如何变化。

若只影响一个预制实例，优先在实例功能或其合适子 Node 中表达；修改共享预制文本或接口前，检查全部实例的影响。不要把画布折叠状态、位置、旧版兼容字段或未确认的代码签名当作功能授权。
